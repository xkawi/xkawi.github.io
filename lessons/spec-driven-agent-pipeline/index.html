Agents that ship when the spec says so

A hands-on course for software engineers. Write a spec, build the eval suite, then hand-build the agent pipeline, tracing and feedback loop around it in Python with the raw Anthropic API. You finish with a working web app and a pipeline you understand line by line.

  • 8 modules, 14 conceptsEach one has ideas with sources, runnable examples, and a guided exercise.
  • One project throughoutA Task Tracker API with cursor paging, then a browser UI, built by the pipeline you write.
  • About 1,100 lines you writeTools, loop, state machine, planner, evaluator, tracing, reports, judge, CLI.
  • Works without spending anythingAn offline mode replays a scripted model, so you can finish the mechanics with no API key.

0.1 The mission, the map, and your environment

Plan on 20 to 40 minutes. No model calls needed except the optional smoke test.

Learn

Three words carry this whole course, so here is exactly how it uses them.

Agent. Anthropic's guide Building effective agents separates workflows, where your code fixes the sequence of LLM calls, from agents, where the model itself decides which tools to call and when to stop. The pipeline you build has both: a fixed outer workflow (plan, generate, evaluate, decide) around an inner agent loop that writes code with tools.

Harness. Everything around the model that is not the model: the system prompt, the tools, the loop, the state, the budgets, and the checks that decide whether work is accepted. Anthropic's engineering posts on long-running agents use the word the same way, and make the point that a model's reliability on a task depends heavily on this surrounding machinery.

Eval. A test for an AI system: you give it an input, then apply grading logic to what it produced. An outcome-based system decides "done" by running that grading on the artifact, never by trusting the agent's own claim that it finished.

1.1 Outcome-based specs and acceptance criteria

Plan on 30 to 45 minutes, mostly thinking.

Learn

A spec does for an agent what it does for a contractor: it removes the need to guess. The cost of a guess is higher with an LLM, because it guesses fluently. A wrong assumption arrives looking like a deliberate design decision, and nothing in the output tells you which parts were assumed.

From feature descriptions to outcome statements

"Build a task tracker with CRUD endpoints" is a feature description. Two competent engineers would build two different systems and both would be right. An outcome statement names something an observer can check: a request, the exact response, and the failure cases. "A POST /tasks with {"title": "Buy milk"} returns 201 and {"id": <integer>, "title": "Buy milk", "completed": false}" can be turned into a test without asking anyone a question.

Acceptance criteria are the unit of "done"

Give every criterion a stable ID (AC-LIST-8). Two things follow. First, the pipeline can report progress as "22 of 26 criteria pass" rather than "mostly works". Second, you can enforce traceability: every ID must have at least one eval, and every eval must name its ID. A criterion without an eval is a hole in your definition of done.

The testability contract

Black-box evals need to start your app, so the spec must pin the few implementation facts they depend on: where the app object lives (app.main:app), how the database path is configured (an environment variable, in the spirit of the twelve-factor "config in the environment" rule), and what an error body looks like. These are the project constraints in the spec below. Everything else about the implementation stays free.

Three defects that keep recurring
  • Unspecified ordering. If a list has no stated order, two correct implementations return different orders and an assert response == expected test flakes. Either state the order or state that tests must not assume one.
  • Request and response asymmetry. A spec that tells the client to send nextCursor but never says the server returns it can be implemented perfectly and still be unusable for "load more".
  • Silent scope. A model asked for "a list endpoint" may helpfully add filtering you never asked for, or you may later assume filtering exists. One sentence ("no search; only the parameters listed") closes both.
Two pieces of background this spec leans on

Cursor (keyset) pagination returns a page plus a pointer to where the next page starts, usually the last row's key, and the next query asks for rows after that key. Unlike OFFSET paging it does not skip or repeat rows when data changes between requests, and it stays fast on large tables.

HTTP status semantics. 400 means the request was malformed, 404 means the request was well-formed but the resource does not exist, and 422 means well-formed but semantically invalid. FastAPI answers validation failures with 422 by default. This spec chooses 400, which means an implementer who trusts the framework default violates the spec. That is deliberate: it is a realistic trap for the evals to catch.

How specs fit into spec-driven development

Birgitta Böckeler's analysis on Martin Fowler's site separates three levels: spec-first (write a spec, then use it for the task at hand), spec-anchored (keep the spec afterward and evolve it with the feature), and spec-as-source (humans edit only the spec, never the code). In Module 6 you will regenerate the whole app from a changed spec, which is the spec-as-source end of that range, made safe by the evals. GitHub's open-source Spec Kit is a popular toolkit for the first two levels.

    Background for this code
    Markdown
    A plain-text format with light markup (# headings, - lists, **bold**). The agent reads it as text; the harness also parses it with a regular expression to extract the criterion IDs, which is why every ID is written exactly as **AC-AREA-n**.

    Clamping
    Forcing a value into a range instead of rejecting it: limit=1000 becomes 100, limit=0 becomes 1. AC-LIST-7 pins this down, because 'reasonable' limits differ between implementations.

  2. Count the criteria, so you know the denominator for 'outcome match' from now on.

  3. Audit the spec the way an adversarial implementer would. Pick three criteria and, for each, write two implementations that satisfy the wording but behave differently somewhere the spec is silent. Write them down before you open the answers. The aim is not to find nothing; no spec is complete.

    Gaps that really exist in this spec
    • "200 characters" is ambiguous. Python counts Unicode code points, a database may count bytes, and JavaScript counts UTF-16 units. An emoji title can be 1, 2 or 4 "characters". The evals only test ASCII.
    • Whitespace-only titles (" ") are 3 characters, so they are valid. Is that what you want?
    • Duplicate titles are not mentioned, so they are allowed, and nothing tests it.
    • Huge ids. A 40-digit id is a "positive integer" but overflows SQLite's 64-bit integers. Behavior is unspecified.
    • Concurrency. Two simultaneous toggles of one task are not addressed.

    This is the normal state of a first-draft spec. The loop in Module 6 is how gaps like these get found and closed: an eval fails or an agent surprises you, and you add a criterion.

  4. Commit it. From now on, spec.md is versioned like code, and every run record will store a short hash of the spec it was built from.

2.1 From criteria to executable checks

Plan on 60 to 90 minutes, including writing three tests yourself.

Learn

An eval is a test for an AI system: an input, plus grading logic that scores what comes out. Anthropic's guidance on agent evals sorts graders into three kinds: code-based, model-based, and human. The rule of thumb is to use the cheapest grader that can actually decide the question, and for acceptance criteria like "returns 201 with this body" that is plain code. Model-based graders come back in Module 5, for the things code cannot judge.

Black-box acceptance tests

These tests never import the implementation's internals. They send HTTP requests to the app and judge the responses. That is what lets one suite grade the agent's code, the reference solution, and any future rewrite. The only coupling is the testability contract in the spec: the app lives at app.main:app and reads TASKS_DB.

Traceability by naming

Every test is named test_ac_<area>_<n>_<what>, so test_ac_list_8_cursor_walk_ascending belongs to AC-LIST-8. The evaluator you build in 2.2 groups results by that ID. A criterion passes only if all of its tests pass, and a criterion with no tests counts as failed. The score "outcome match" is then simply criteria passed divided by criteria in the spec.

Isolation

Each test gets a fresh database file and a fresh import of the app. Without that, test order would matter and a bug in one run could hide or fake a bug in another. In Python, import caches modules in sys.modules, so "fresh import" has to be done on purpose, which is what the fixture does.

Held-out tests

The generating agent never sees this test code, only short failure messages. Systems optimize what they can see. If the agent could read the tests, "make these tests pass" and "satisfy the spec" would be two different goals, and a clever agent could hit the first without the second. This general failure is often called specification gaming or reward hacking; Concrete Problems in AI Safety discusses it. Anthropic's eval guidance also notes that capable models can find solutions a static eval did not anticipate, which is a reason to keep the graders out of the agent's reach and to read transcripts.

2.2 Test your tests: oracle, planted bugs, and per-criterion scoring

Plan on 45 to 75 minutes.

Learn

An eval can be wrong in two opposite ways. It can be too lax, passing code that violates the spec, or too strict, rejecting a valid solution because it tests an implementation detail. You find both kinds of error before you trust the suite, with two cheap checks:

  • An oracle must pass. A reference implementation, written by a human, should score 26 of 26. If it does not, either the tests or the reference is wrong, and the agent was never going to win. It is a standard sanity check in eval design: confirm that a task can be solved before you measure anything on it.
  • Known-bad variants must fail. Plant a bug and confirm the right criteria go red. This is mutation testing in miniature. If planting a bug changes nothing, the suite cannot see that class of bug.
Turning test output into a score

pytest can emit a JUnit XML report, a standard machine-readable test format that CI systems have consumed for years. The evaluator runs pytest in a separate process (so a crashing or hanging app cannot take down the harness, and a timeout can be enforced), parses the XML, groups test results by criterion ID, and returns a report object with a score and a feedback() method.

feedback() is the only channel from the hidden tests to the generator. It lists failing criteria with a short message and lists passing ones as "do not break". Treat what goes through that method as part of your agent's prompt, because it is.

Pass-to-pass and fail-to-pass

Anthropic's eval write-up distinguishes tests that should flip from failing to passing (the new work) from tests that should stay passing (regressions). Our single score hides that, but the per-criterion map does not: a retry that fixes four criteria and breaks two others is visible as exactly that. You will use this in Modules 5 and 6.

3.1 Tool use and the raw agent loop

Plan on 60 to 90 minutes. Live steps need an API key.

Learn

The model API is stateless: every call sends the whole conversation so far, and the model replies with one more message. There is no session on the server. "The agent remembers what it did" is simply your code resending a growing list.

Tool use is a protocol, not magic

You describe tools to the model as a name, a description, and a JSON Schema for the input. The model never runs anything. When it wants to use a tool it emits a tool_use block (an id, the tool name, and the input object) and stops with stop_reason: "tool_use". Your code runs the tool and sends the output back in a tool_result block whose tool_use_id matches. Then you call the model again.

That is the whole agent loop: call, run what it asked for, append results, repeat until it stops asking. A framework adds conveniences on top of this; it does not replace it. Building it by hand once is the best way to understand what every framework hides.

Details that cause real bugs
  • Parallel tool calls. One assistant turn can contain several tool_use blocks. Every one needs a matching tool_result, and all of them go back together in a single user message.
  • Keep that message clean. Anthropic's stop-reason guidance warns against appending extra text right after tool results; send the results alone.
  • Errors are information. If a tool fails, set is_error: true on the result and say what went wrong. The model can often fix its own call. Our toolbox raises a ToolError for problems the model should see, and the loop converts it.
  • Budgets. A loop without a cap is an invoice waiting to happen. max_turns bounds model calls; max_tokens bounds each reply. If a reply is cut off by max_tokens in the middle of a tool call, the call is incomplete; treat it as a failure, not as a result.
  • Return why you stopped. end_turn (the model finished) and max_turns (you stopped it) must be distinguishable, because only one of them is a claim of success.
Security: the model's output is untrusted input

A tool call is text produced by a program you do not control, about to be executed on your machine. The toolbox below confines file access to one directory (defending against path traversal such as ../../.ssh/id_rsa), enforces a timeout on commands, truncates output, and hides environment variables ending in _KEY from the shell. It is not a sandbox: run_command uses a real shell. For anything beyond a personal experiment, run the whole harness in a container that mounts only the project directory.

3.2 Explicit state and control flow

Plan on 60 to 90 minutes. Runs entirely offline.

Learn

A real pipeline has more going on than one loop: planning, repeated attempts, evaluation, budgets. The usual first design is a single long conversation that carries everything. It becomes impossible to inspect, to test, or to resume. The alternative used here is to keep everything a run knows in one explicit state object, and to drive control flow with small functions over that state.

Nodes return the name of the next node

Each step (plan, generate, evaluate, decide) is a plain function that receives the state, does its work, updates the state, and returns the name of the next node. A dictionary maps names to functions, and a while loop follows the names until it reaches "end". That is the entire mechanism. Graph frameworks such as LangGraph give you the same ideas (state, nodes, edges) with persistence, visualization, and human-in-the-loop on top, and their documentation describes it in those words: nodes do the work, edges decide what runs next.

The evaluator-optimizer pattern

Anthropic's agent guide names this shape: one component generates, another evaluates and gives feedback, in a loop. It works best when the criteria are clear and when iteration measurably helps, which is exactly our situation. Here the evaluator is the hidden test suite rather than another model.

Fresh conversation, persistent workspace

Each attempt starts a new model conversation. What carries over is (a) the files already in the workspace and (b) a compact feedback summary. A long agent transcript can be tens of thousands of tokens, and resending it makes every later call slower, costlier, and more confusing. Using files and short notes as the memory between sessions is the same idea Anthropic describes for long-running coding agents.

Stopping conditions belong to the outer layer

Three guards live in the state machine: max_attempts (budget), stuck_limit (stop when the same criteria keep failing instead of paying to repeat a failed approach), and a hard cap on node transitions (a bug in your own edge logic must not loop forever). The run ends with a status: passed, stuck, exhausted, or error. "It stopped" and "it succeeded" are different facts.

Test doubles for the model

The harness is mostly ordinary code: state transitions, budgets, parsing. You should be able to test it without a network and without randomness. A test double (here a fake) is a stand-in object with the same interface as the real thing. Because the harness only ever calls client.messages.create(...), any object with that method works, including one that replays a scripted conversation. That is what fake_llm.py is: it lets you watch the retry loop, the stuck detector and the run record work, for free, deterministically.

3.3 Planner, generator, evaluator: separating the roles

Plan on 45 to 60 minutes. Offline, with one optional live step.

Learn

The pipeline has three roles with three different jobs, and keeping them separate is what makes the result trustworthy.

  • Planner: turns the spec into an ordered checklist and a list of risks. It writes no code.
  • Generator: the tool-using agent from 3.1 that writes and runs code.
  • Evaluator: decides whether the result meets the spec. Here it is the hidden test suite from Module 2.
Why the evaluator must be a different thing

Asking the generator "is your work correct?" invites a biased answer. There is direct evidence for a version of this: Panickssery, Bowman and Feng (NeurIPS 2024) found that language-model evaluators tend to rate their own outputs higher than outputs from other models or humans, and that the effect grows with how well the model can recognize its own writing. Anthropic's write-up of a harness for long-running application development similarly describes a separate evaluator alongside the generator. Our evaluator is plain code, which is the strongest separation available: it shares no model, no context and no incentive with the generator. When a quality judgment needs a model (Module 5), it will use a different model and a different prompt.

The interactive toy model below makes the mechanism concrete. It is a simulation of a mechanism, not a measurement of any real model.

Structured output from a forced tool call

The planner must return something your code can parse. Instead of asking for JSON in prose and hoping, define a tool whose input_schema is the shape you want and set tool_choice to force that specific tool. The model's reply is then a tool_use block whose input follows your schema. (Anthropic's docs also describe an opt-in strict mode on tool definitions for schema guarantees; read the tool-use docs for current details.)

Trust, but verify the model's output

Even schema-shaped output can be wrong. ensure_coverage checks the one property we can verify mechanically, that every criterion ID appears in some step, and patches the plan if not. The general habit: wherever a model's output feeds code, put a deterministic validator between them.

Does the planner help? Do not assume

A planning step costs tokens and can mislead as easily as help. Whether it improves outcomes for this task is an empirical question, and Module 5 shows how to answer it with trials. That is why use_planner is a setting.

4.1 Traces, spans and Langfuse

Plan on 60 to 120 minutes, most of it the first Docker start and exploring the UI.

Learn

When an agent run goes wrong, the question is never "did it fail?" but "which step made it fail, and what did that step see?" A log line saying "agent finished" cannot answer that. An agent run is a loop with branching: model calls, tool calls, retries, nested sub-steps. You need the whole tree, with inputs and outputs at every node.

Traces and observations

A trace is one end-to-end run. It contains observations (called spans in OpenTelemetry), each representing a unit of work with a start, an end, an input, an output, and a parent. Observations nest: the run contains an attempt, the attempt contains a model call, and so on. Langfuse adds types that make agent traces readable: generation (an LLM call, with model and token usage), tool, agent, chain, evaluator, and a generic span.

How nesting happens without you passing anything around

The SDK's @observe decorator wraps a function in an observation and stores it in a context variable (the OpenTelemetry current context). Any decorated function called inside it finds that context and becomes its child. That is why adding one decorator line per function is enough to reconstruct the call tree, and why the tree in this course mirrors the call structure of the harness. If you have used async frameworks or distributed tracing, this is the same mechanism.

What to record
  • Input and output of each step, so you can see what the model saw and what it did.
  • Model and token usage on generations, so cost and latency are visible per step and per run.
  • Scores attached to the trace. We attach outcome_match after every evaluation, which turns "how did this run do?" into something you can filter and chart.
  • Attributes like a session id (we use the run id) and tags (we use your --tag), so related runs group together and you can find the baseline again.
Practicalities worth knowing
  • Export is asynchronous and batched. The SDK queues spans and sends them in the background. A short-lived script can exit before the queue drains, so call flush() before the process ends. run_pipeline does.
  • Tracing must never break the run. Our tracing.py turns every call into a no-op if the keys are unset, and swallows and reports its own errors. Observability is a guest in your program.
  • Traces contain your prompts, spec, code and tool output. That is the point, and also why people self-host. Treat the trace store like a log store that holds source code.
  • SDKs move. Version 4 replaced update_current_trace with propagate_attributes and moved input/output onto observations. Pin the major version and read the migration guide when you upgrade.

5.1 Run records, variance and comparing configurations

Plan on 45 minutes offline; the live experiment adds time and cost.

Learn

One run of a stochastic system is an anecdote. If a run passes, you do not know whether the pipeline is good or the run was lucky; if it fails, you do not know whether to change something or just try again. Evaluating agents means measuring a distribution: run the same task several times and look at the results together.

The vocabulary

Anthropic's guide to agent evals uses these terms, and so does this course: a task is one problem with a defined success criterion (here, the spec); a trial is one attempt at a task; an outcome is the final state of the environment (here, the generated project); a grader scores it. Because trials vary, you run several per task.

pass@k and pass^k

Two summaries answer different questions. pass@k asks whether at least one of k trials succeeded, which matters when you can retry, such as a developer picking the best of a few suggestions. The metric comes from code-generation evaluation (Chen et al., 2021). pass^k asks whether all k trials succeeded, which matters when users expect consistency, such as an unattended pipeline that must work every time. If a single trial succeeds with probability p and trials are independent, pass@k is 1 − (1 − p)k and pass^k is pk. At k = 1 they are identical; as k grows, one heads to 100% and the other to 0%. For a fully autonomous "PM defines it, agents ship it" pipeline, pass^k is the honest number.

Designing a fair comparison
  • Change one thing. A planner on versus off, one prompt line, one model. If you change two, you cannot attribute the difference.
  • Hold the rest fixed. Same spec (the record stores its hash), same evals, same limits. Tag runs by arm so they can be grouped.
  • Write your hypothesis first. It keeps you honest about what you expected and prevents explaining any result after the fact.
  • Look beyond the headline. Per-criterion rates show where an arm differs, and the regression list shows what got worse. A change that raises the average while breaking one criterion is not free.
  • Respect small samples. With three trials per arm, "3 of 3 versus 2 of 3" can easily be chance. Treat small experiments as hints that tell you where to look, then confirm with more trials or by reading transcripts.
  • Read the transcripts. Numbers tell you whether; transcripts tell you why. Anthropic's guidance is explicit that reading transcripts is how you validate graders and catch unfair scoring.
Capability evals versus regression evals

Capability evals ask "can it do this hard thing?" and start with low pass rates. Regression evals ask "does it still do everything it used to?" and should stay near 100%. A capability eval that the pipeline now passes consistently graduates into the regression suite. Your 26 criteria are both: they define the target and, once passing, guard against backsliding.

5.2 LLM-as-judge for what tests cannot see

Plan on 60 minutes offline; the live calibration adds a little.

Learn

Your 26 criteria pass and the project can still be unacceptable. Recall the planted bug q1 from Module 2: it builds SQL with an f-string and leaves a print in the code, and passes everything, because behavior through HTTP is identical. Functional tests cannot see properties that do not change behavior: injection-prone SQL, structure, leftovers, readability. Two kinds of grader cover them.

Deterministic first: static analysis

Many quality properties can be checked mechanically by reading the code's structure. Python's ast module parses source into a tree, so "does any execute() call receive an f-string?" becomes a short tree walk. Prefer this wherever it is possible: it is free, repeatable, and has no opinions. Its weakness is that it only sees what you taught it to look for. The check in judge.py inspects the argument passed directly to execute, so it misses SQL that was assembled into a variable first.

Model-based graders for the rest

When the property needs judgment ("is error handling consistent?"), use a model as a grader. Design rules that matter:

  • One criterion per question, answered pass, fail or unknown. An "unknown" option stops the judge from inventing a verdict when the code does not show enough.
  • Demand evidence. Require a file and line or a short quote with every verdict. It makes verdicts auditable and tends to make them more careful.
  • Structured output via a forced tool call, as with the planner, so the result is parseable.
  • Independence from the generator. Use a different model and a fresh context, and show it only the artifact, never the generator's reasoning. Self-preference bias (3.3) is the reason.
  • Know the known biases. The MT-Bench judge study (Zheng et al.) documents position bias, verbosity bias and self-enhancement bias in LLM judges.
Calibrate before you trust

A judge is an instrument, and instruments get calibrated. Compare its verdicts with something you trust: a deterministic check where one exists, and your own labels everywhere else. Hamel Husain's approach is to have a domain expert make binary pass/fail calls with short critiques, then iterate on the judge's prompt until it agrees with them. Where the judge and the check disagree, read the evidence and decide who is right; sometimes the judge has found a real gap and sometimes the check is naive. Start the judge as an advisory signal, and promote it to a gate only after it has earned trust.

6.1 Triage, fix one thing, verify

Plan on 60 to 120 minutes, mostly waiting for trials.

Learn

You now have the instruments: per-criterion results, run records, traces, comparisons. The feedback layer is the habit of using them in a fixed loop instead of changing things by feel:

observe a failure, hypothesize its cause, change exactly one thing, re-run enough trials, compare, then keep or revert.

Four levers, roughly in order of cost and how often they are the right one
  1. The spec. The failing check reveals that the spec was ambiguous or silent, and the agent made a reasonable guess you did not want. Fixing the spec helps every future run and every future engineer. It is the cheapest and most underused lever. Test: is the agent's behavior a reasonable reading of the words in the spec? If yes, the spec is the problem.
  2. The prompt and the harness. The spec was clear but the agent mis-applied it. Fix the instructions, the plan, the feedback it receives, or the budgets. A cryptic failure message (assert 4 is None) is a harness defect: the feedback is part of the agent's prompt.
  3. Tools and context. The agent lacked information or a capability: it could not run the tests, a tool's output was truncated, a framework's documentation was missing. Fix what it can see and do.
  4. The model. A stronger model, a different split of roles, or, last, training. Fine-tuning needs a large set of labelled failures to be worth anything, and most teams get the value from the first three levers. Tools such as DSPy automate prompt optimization against an eval set, which sits between levers 2 and 4.

Anthropic's write-up on long-running agent harnesses lists specific failure modes (declaring the job done too early, losing context between sessions) next to structural fixes, which is lever 2 and 3 thinking: change the machinery, not the model.

How to choose with evidence
  • Failure is the same every trial and a reader would agree the agent's reading was fair: spec.
  • Failure is the same every trial, the spec was clear, and the transcript shows the information was available but not used: prompt or feedback.
  • The transcript shows the agent could not do something it needed to: tools or context.
  • Failure comes and goes with identical inputs: variance. Measure it with more trials; consider the model, or accept and design around it.
Habits that keep the loop honest
  • One change per experiment, recorded in a notebook with the hypothesis, the tag, and the outcome. Reverting should be one git command.
  • Check regressions, not just improvements. compare lists criteria that got worse; a "win" that breaks something else is a trade, not a win.
  • Do not overfit your evals. If you tune prompts until these 26 criteria pass, the suite measures how well you fit it. Keep some tasks you have not tuned against; 6.2 gives you one.
  • Start from real failures. Anthropic's eval guidance recommends building from actual failures, and Hamel Husain's work on error analysis makes the same point: read the data before designing the fix.

Spec as source

In Module 1 we met the spectrum from spec-first to spec-as-source. This module takes the far end: we do not edit the generated API to add a UI. We change the spec and regenerate the whole project from it. That is only safe because the evals decide whether the regenerated project is acceptable. Change the spec, run the pipeline, trust the criteria.

Evaluating a UI with static checks, and their limits

Judging a real browser UI normally needs a browser. Our evals do something cheaper and cruder: they fetch the page and check what the server sends. The spec pins a test-id contract (data-testid attributes that name the important elements), which gives a stable handle for tests no matter how the page is styled. The checks confirm that the elements exist and that the script calls /tasks.

These are proxies: a page can contain all the right strings and still not work. Treat them as a floor. The next step up is a browser-driven test (Playwright for Python is a common choice) that actually clicks "Add task" and asserts that the item appears; that is a natural next criterion to add.

Why AC-UI-5 bans innerHTML

If a page inserts user text with innerHTML, text that looks like HTML is parsed as HTML. A task titled <img src=x onerror=alert(1)> would then run script in every viewer's browser: cross-site scripting (XSS). Setting textContent treats the same string as plain text. The criterion encodes this as a checkable rule ("never uses innerHTML"). It is a proxy for "does not inject untrusted HTML", and you will see both sides of it in the exercise.

7.1 From scripts to an installable framework

What was already generic
  • The state machine (plan, generate, evaluate, decide), the budgets, and the stuck detector know nothing about task trackers.
  • The evaluator works for any project where tests follow two conventions: test names carry criterion IDs, and a --workspace option points the suite at the code under test. It consumes standard JUnit XML, and nearly every language ecosystem has a way to emit JUnit XML, so the same idea extends beyond Python.
  • The tools, tracing wrapper, run records, compare and triage are project-agnostic.
What was project-specific, and where it now lives
  • The spec and the evals: per project, in spec.md and evals/.
  • Model and budget choices: taskforge.yaml.
  • Know-how about the stack (for example "FastAPI returns 422 by default"): prompt_extra in the config rather than a constant in code. That one setting is what stopped the generator prompt from being tied to FastAPI.
Packaging: making it a command

A pyproject.toml with a [project.scripts] entry declares a console command: taskforge = "harness.cli:main" means "installing this package creates a taskforge executable that calls main()". An editable install (pip install -e .) is how you develop it. Files that are not Python modules, like the scaffold templates, must be declared as package data to be installed with the package.

Scaffolding: taskforge init

The fastest way to make a framework usable is a command that creates a working starter project: a spec with one criterion, an eval for it, a reference app that passes, and a config. The user can run taskforge run --offline within a minute and see the whole loop before writing anything. The offline fake replays the scaffold's reference/ app, which is why the scaffold ships one.

Design judgments to make before you generalize further
  • Who writes the evals? In this course, a human did. Having a model generate them from the spec is tempting, but a model drafting tests inherits the same misunderstandings as the model writing the code. If you do it, treat generated evals as drafts and validate them the way you did in 2.2: an oracle must pass and planted bugs must fail.
  • Adopt versus build. Orchestration, tracing, spec scaffolding and eval harnesses already exist as maintained tools. A framework is most valuable when it integrates them with sensible defaults, not when it reimplements each. Build the seams.
  • Isolation. A tool that runs model-written shell commands should run them in a container by default. This is the first thing to add before anyone else uses it.
  • Cost controls. Per-run and per-session token budgets, enforced, not just recorded.
  • Local-first. Running Langfuse from a Docker Compose file keeps traces on the user's machine, which matters because traces contain their source code.

B. Glossary

Acceptance criterion
One checkable statement about observable behavior, with a stable ID (AC-LIST-8). The spec's unit of 'done'.
Agent
A system where an LLM decides which tools to call and when to stop. Contrast with a workflow, where your code fixes the sequence.
Context window
The maximum amount of text (in tokens) a model can consider in one call: system prompt, history, tool results and its own reply.
Eval
A test for an AI system: an input plus grading logic applied to the output.
Evaluator-optimizer
A workflow pattern in which one component generates, another evaluates and gives feedback, and the loop repeats.
Fake / test double
A stand-in object with the same interface as a real dependency, used so you can test your own logic deterministically and for free.
Generation (observation type)
An observation that represents one LLM call, carrying model name, token usage and output.
Grader
The logic that scores an outcome: code (a test), a model (a judge), or a human.
Harness
Everything around the model: prompts, tools, loop, state, budgets, and the checks that decide whether work is accepted.
Held-out test
A test the agent never sees, so that passing it is meaningful evidence of meeting the spec.
Keyset (cursor) pagination
Paging by remembering the last key you returned and asking for rows after it, instead of skipping N rows.
Mutant
A copy of working code with one deliberately planted bug, used to check that tests can fail.
Observation / span
One unit of work inside a trace, with a start, end, input, output and parent.
OpenTelemetry (OTel)
A vendor-neutral standard for traces, metrics and logs. Langfuse's Python SDK builds on it.
Oracle (reference implementation)
A human-written solution that must pass the evals, used to prove the evals are fair.
Outcome-based
Deciding that work is done by grading the produced artifact, not by trusting the agent's report.
pass@k / pass^k
The probability that at least one of k trials succeeds, versus that all k succeed.
Reward hacking / specification gaming
A system satisfying the letter of its objective in a way that defeats its intent, for example by exploiting graders it can see.
Self-preference bias
The tendency of an LLM evaluator to rate its own outputs higher than equally good outputs from other sources.
stop_reason
The field on a model response that says why generation ended: end_turn, tool_use, max_tokens, and others.
System prompt
Instructions given to the model separately from the conversation, setting its role and rules for the whole call.
Token
A sub-word chunk of text. Models read and write tokens, and APIs bill by them.
Tool use
A protocol where the model emits a structured request to call a function you defined, and your code runs it and returns the result.
Trace
The record of one end-to-end run as a tree of observations.
Trial
One attempt at a task. You run several, because results vary.
Workspace
In this course, the directory where the agent writes the generated project for one run.
